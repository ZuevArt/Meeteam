## Что относится к текущей реализации

В RAT-PoC каталог из восьми источников хранится в `data/state.json`; PostgreSQL ещё не подключена к Go API. [План прототипа](docs/План-этапа-Прототип.md) предусматривает PostgreSQL для событий, пользователей, команд и заявок. Для этого квеста создана **реальная тестовая таблица событий Meeteam** и проверен путь миграции заполненной БД. Это фундамент будущего переноса, а не заявление о том, что нынешний сервер уже читает PostgreSQL.

Рабочие файлы: [тестовая PostgreSQL](compose.quest7.yml), [команды](scripts/quest7-db.ps1), [начальная таблица событий](db/migrations/0001_create_events.sql), [новое поле и индекс](db/migrations/0002_event_team_eligibility.sql), [три тестовых события](db/seed/quest7_events.sql). ## 1. Политика миграций

Выбраны **последовательные SQL-файлы и PowerShell runner**. Файлы находятся в `db/migrations`, имя имеет вид `0001_описание.sql`, `0002_описание.sql` и т. д. Runner сортирует их по имени, применяет отсутствующие по порядку, записывает SHA-256 содержимого и отказывается работать, если уже применённый файл изменился. Каждая миграция и запись о ней выполняются одной транзакцией PostgreSQL (`psql --single-transaction -v ON_ERROR_STOP=1`). Таблица учёта создаётся runner при первом запуске:

| Поле `schema_migrations` | Смысл |
|---|---|
| `version text PRIMARY KEY` | Точное имя применённого SQL-файла; уникальный порядок задаётся префиксом |
| `checksum_sha256 char(64)` | Хеш содержимого файла, защита от изменения уже применённой версии |
| `applied_at timestamptz` | Фактическое время успешного применения в UTC/часовом поясе сессии |

Проверенный пример из тестовой БД: `0001_create_events.sql` с хешем `5181210D…17682` применена **14.11.2026 10:30:49 UTC**, `0002_event_team_eligibility.sql` с хешем `3A9B2B8D…EC798` — **10:31:09 UTC**. Это две строки, а не «текущая версия 2»: журнал сохраняет историю применения.

### Команды для другого участника (PowerShell, из корня репозитория)

Нужны Docker Desktop, PowerShell и клиентские программы PostgreSQL 17 (`psql`, `pg_dump`, `pg_restore`, `createdb`) — в `PATH` или в `$env:PG_BIN` (папка `bin`). В данном тесте использовалась локальная установка `C:\Program Files\PostgreSQL\17\bin`. Контейнер слушает **только `127.0.0.1:55432`**, использует доверенную локальную авторизацию исключительно для тестовой БД. На внешнем интерфейсе или в production такой способ авторизации применять нельзя.

```powershell
docker compose -p meeteam-q7 -f compose.quest7.yml up -d --wait
./scripts/quest7-db.ps1 -Action status
./scripts/quest7-db.ps1 -Action migrate -To 1
./scripts/quest7-db.ps1 -Action seed
./scripts/quest7-db.ps1 -Action migrate
./scripts/quest7-db.ps1 -Action status
./scripts/quest7-db.ps1 -Action migrate  # повтор: только already applied
```

На новом томе Compose создаёт пустую `meeteam_quest7`. `-To 1` нужен именно для демонстрации миграции **после** вставки записей; в обычном развёртывании выполняется просто `-Action migrate` до запуска API/worker. Для новой миграции:

```powershell
./scripts/quest7-db.ps1 -Action new -Name add_event_description
Get-Content db/migrations/0003_add_event_description.sql
# заполнить и проверить SQL; затем:
./scripts/quest7-db.ps1 -Action status
./scripts/quest7-db.ps1 -Action migrate
```

Команда `new` показана как процедура для будущего изменения; файл `0003` в этом квесте не создавался. Уже применённые `0001` и `0002` **не редактируются**. Перед объединением новой версии разработчик проверяет SQL на пустой и заполненной тестовой БД, запускает `status`, проверяет данные и повторный запуск. На развёртывании порядок: БД и healthcheck → миграции → Go API/worker → веб-клиент. При ошибке транзакция миграции и запись в журнал откатываются; приложение не запускается на неопределённой схеме. Автоматических `down`-миграций нет: удаление поля может потерять данные. Исправление уже применённой схемы — новой миграцией вперёд; аварийный возврат — из проверенной копии в отдельную БД с последующим контролируемым переключением.

## 2. Политика резервного копирования

**Что копируется сейчас:** логический дамп PostgreSQL в custom format (`pg_dump -F c`) и, если существует, текущий PoC-файл `data/state.json`. Для каждого файла записывается SHA-256 в `manifest.json`; дамп дополнительно проверяется `pg_restore --list`. PostgreSQL и JSON пока независимые хранилища, поэтому единой транзакционной точки между ними нет. При переходе API на PostgreSQL события и пользовательские данные будут в одной БД. Когда появятся аватары в S3/MinIO, копия БД должна сопровождаться снимком версионированных объектов и общим идентификатором набора; восстановление проверяется для пары «БД + файлы». Сейчас пользовательских файлов в проекте нет.

**Целевые RPO/RTO для прототипа с регистрацией:** потеря не более **1 часа** пользовательских изменений (RPO), восстановление сервиса в пределах **2 часов** (RTO). Основание: при небольшом пилоте почасовой логический дамп практически выполним, а заявки и решения капитана нельзя восстанавливать только повторным импортом. Для импортированного каталога допустима более старая копия, поскольку его можно пополнить повторным импортом; это не относится к профилям и заявкам. Значения — проектные цели до первых измерений, **локальный разовый тест не доказывает соблюдение RPO/RTO**.

**После развёртывания:** запускать копирование каждый час отдельным заданием; размещать копии вне диска/сервера PostgreSQL (например, в отдельном объектном хранилище), доступ только у ответственных за восстановление; шифровать при переносе и хранении. Сообщать ответственному об ошибке задания, невалидном дампе или отсутствии свежей копии более часа. Хранить **14 дней**, но всегда сохранять как минимум самую свежую проверенную копию. Проверять восстановление на отдельной БД не реже раза в месяц и после существенной смены схемы. Расписание, внешнее хранилище и оповещение **пока не настроены**: это работа развёртывания прототипа из плана.

**Локально проверено:** ручное создание, хеширование, восстановление и очистка. По умолчанию скрипт использует `$env:TEMP\meeteam-quest7-backups`, вне репозитория. Для рабочего окружения путь задают через `-BackupDir` или `MEETEAM_BACKUP_DIR`; он должен указывать на отдельное хранилище. Каталог `backups/` и `*.dump` исключены из Git. Секреты подключения задаются окружением PostgreSQL и в отчёт не записываются.

### Повторяемые команды

```powershell
$backupDir = Join-Path $env:TEMP 'meeteam-quest7-backups'
./scripts/quest7-db.ps1 -Action backup -BackupDir $backupDir
# скопируйте имя meeteam-YYYYMMDDTHHMMSSfffZ из вывода:
./scripts/quest7-db.ps1 -Action restore -BackupDir $backupDir -BackupName 'meeteam-20261114T103139112Z' -RestoreDatabase 'meeteam_quest7_restored'
./scripts/quest7-db.ps1 -Action prune -BackupDir $backupDir -RetentionDays 14       # сначала список
./scripts/quest7-db.ps1 -Action prune -BackupDir $backupDir -RetentionDays 14 -Apply # затем удаление
```

`restore` требует **новую пустую БД**, отказывается писать в `meeteam_quest7`, проверяет контрольную сумму и восстанавливает все объекты через `pg_restore --exit-on-error`. Если в копии есть `state.json`, он остаётся в папке копии: для проверки его следует скопировать в отдельный тестовый `STATE_FILE`, не перезаписывая действующий файл сервиса. Очистка работает только внутри явно указанного каталога, выбирает папки заданного шаблона с валидным manifest/дампом, сначала показывает `WOULD DELETE`, а при `-Apply` удаляет старые; свежая проверенная копия защищена независимо от даты.

14 ноября создана копия `meeteam-20261114T103139112Z`. `pg_restore --list` прочитал дамп, SHA-256 записан в manifest; присутствующий `data/state.json` скопирован с отдельным SHA-256. Из копии создана **другая** БД `meeteam_quest7_restored`. В ней запрос вернул те же три записи и поле `team_eligibility='unknown'`:

```text

quest7-devpost-1  | Meeteam Test Hackathon | unknown
quest7-hacklist-2 | Meeteam Data Challenge | unknown
```

Для проверки очистки сделаны **две копии проверенного дампа с искусственно старыми именами** `meeteam-20261001T000000000Z` и `meeteam-20261020T000000000Z`. Это тестовые дубликаты, а не реальные исторические бэкапы. Dry-run показал `WOULD DELETE` для обеих и `KEEP` для `meeteam-20261114T103139112Z`. После `-Apply` обе старые копии удалены, свежая проверенная копия осталась одна. Следующий `restore` можно выполнить с новым именем отдельной БД, чтобы вновь подтвердить её пригодность.
