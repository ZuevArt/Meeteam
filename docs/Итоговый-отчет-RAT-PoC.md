# Итоговый отчёт по RAT‑PoC Meeteam

Дата фиксации результата: 16 октября 2026 года.

## 1. Цель работы

Цель RAT‑PoC — проверить главный технический риск сервиса поиска команд: можно ли регулярно собирать актуальные мероприятия с независимых внешних площадок, привести несовместимые форматы к единой модели и продолжать показывать пользователю последнюю достоверную выборку при отказе одного из источников.

В прототипе проверены восемь источников:

1. Хакатоны.рус;
2. Codenrock;
3. Hackathons.pro;
4. HackathonRadar;
5. Kaggle;
6. HackList;
7. Devpost;
8. Devfolio.

Основной вывод: риск преодолим. Для каждого источника удалось подобрать отдельную стратегию получения данных, а единый контракт адаптера изолирует остальную систему от различий между JSON, HTML, Next.js/Tilda и страницами, требующими выполнения JavaScript.

## 2. Что входит в текущий вертикальный срез

Система состоит из следующих частей:

- восемь независимых Go-адаптеров;
- единая нормализованная модель мероприятия;
- оркестратор импорта и журнал запусков;
- файловое JSON-хранилище с атомарной записью;
- HTTP API на Go;
- одностраничный интерфейс на React и TypeScript;
- паспорта источников и отдельные RAT-отчёты по результатам живых проверок.

Общий поток данных:

```text
Публичный сайт или endpoint
          ↓
  адаптер конкретного источника
          ↓
 получение → разбор → нормализация → валидация → дедупликация
          ↓
     ImportResult + rejected
          ↓
 атомарный JSON-снимок и журнал запусков
          ↓
        Go HTTP API
          ↓
       React-каталог
```

Адаптеры не передают во фронтенд исходную структуру сайтов. Каждый из них формирует одну и ту же модель `Event`, поэтому интерфейс не зависит от того, как именно конкретная площадка публикует данные.

## 3. Как выполняется импорт

### 3.1. Запуск

При старте приложения регистрируются все источники в фиксированном порядке. Если `AUTO_IMPORT=true`, адаптеры запускаются последовательно. Любой источник можно обновить отдельно запросом `POST /api/imports/{source}` или кнопкой «Запустить импорт» в интерфейсе.

В один момент времени выполняется только один импорт. Параллельный запрос получает HTTP `409`, поэтому два тяжёлых браузерных процесса или две конкурентные записи состояния не запускаются одновременно.

### 3.2. Получение данных

Каждый адаптер самостоятельно решает, как читать свой источник:

| Источник | Способ получения | Как ограничивается выборка |
|---|---|---|
| Хакатоны.рус | Публичные JSON endpoint Tilda | Лента ближайших событий, затем детали карточек |
| Codenrock | Отрисованная публичная страница в headless Chrome | Текущий и будущие доступные месяцы, максимум 12 месяцев |
| Hackathons.pro | Публичные JSON endpoint Tilda | Все страницы активного feed, завершившиеся события отбрасываются |
| HackathonRadar | Серверный Next.js payload публичной таблицы | Все доступные публичные страницы, стабильная сортировка по названию |
| Kaggle | Публичный каталог и детали в headless Chrome | Фильтр `active`; бессрочные карточки `Ongoing` исключаются |
| HackList | Серверный HTML и Schema.org `Event` | Только секция «регистрация открыта» |
| Devpost | Публичный JSON-каталог | `status=open`, все страницы |
| Devfolio | Публичный search endpoint веб-клиента | `type=application_open`, пагинация `from`/`size` |

HTTP-адаптеры ограничивают частоту запросов и повторяют временные ошибки. Codenrock и Kaggle используют Chrome только потому, что их полезное содержимое появляется после выполнения JavaScript; остальные источники обрабатываются обычными HTTP-запросами.

### 3.3. Нормализация

В общую карточку переносятся только подтверждаемые данные:

- внутренний ID вида `<source_id>:<source_event_id>`;
- источник и устойчивый ID записи на стороне источника;
- название и описание;
- дата начала и окончания;
- точность даты: день, месяц или точное время;
- срок регистрации и срок актуальности карточки, если они опубликованы;
- формат: `online`, `offline` или `hybrid`;
- организатор;
- официальная ссылка и ссылка исходной карточки;
- изображение и теги;
- пояснения о способе разбора;
- SHA‑256 fingerprint нормализуемых полей;
- время первого и последнего наблюдения карточки.

Адаптер не заполняет поле догадкой, если источник не позволяет подтвердить его значение. Например, дата публикации Tilda не считается датой мероприятия, а запись только с формулировкой «подать до …» отклоняется, если из неё нельзя достоверно получить начало события.

### 3.4. Валидация и частичный успех

У каждого источника есть набор обязательных полей. Обычно это ID, название, дата, URL карточки и ссылка участия. Некорректная отдельная карточка помещается в `rejected` с причиной, а остальные карточки продолжают обрабатываться.

Результат запуска получает один из статусов:

- `never` — источник ещё не запускался;
- `running` — импорт выполняется;
- `success` — все полученные записи валидны;
- `partial` — часть записей импортирована, часть отклонена;
- `failed` — цикл целиком не дал безопасного результата.

Пустой каталог или ноль валидных карточек не считаются нормальным успешным ответом. Это важно: внезапные `0 событий` чаще означают изменение сайта или блокировку, а не реальное исчезновение всех мероприятий.

## 4. Хранение данных

На этапе PoC используется `data/state.json`. Файл содержит:

- карту событий по стабильному внутреннему ID;
- состояние каждого источника;
- до 30 последних запусков импорта.

При повторном импорте карточка с тем же ID обновляется, но сохраняет `first_seen_at`; `last_seen_at` получает время нового успешного цикла. Дубли внутри одного источника удаляются до записи.

Сохранение выполняется атомарно: новое состояние сначала записывается в `state.json.tmp`, затем заменяет основной файл операцией rename. Если запись временного файла не удалась, существующий снимок остаётся на месте.

`data/state.json` исключён из Git: локальные импортированные данные не попадут в репозиторий. В Git остаётся только пустой `data/.gitkeep`.

### Текущее ограничение хранилища

Успешный импорт выполняет upsert, но пока не удаляет и не деактивирует старые карточки того же источника, которые исчезли из новой выборки. Поэтому прототип гарантирует сохранность данных при сбое, но ещё не реализует полный жизненный цикл удаления устаревших записей.

Для следующего этапа нужен source-scoped snapshot: после полностью успешного импорта записи источника, не встреченные в новом цикле, следует помечать неактивными или архивировать. При `partial` и `failed` удалять их нельзя.

## 5. HTTP API и интерфейс

Backend предоставляет:

- `GET /api/health` — состояние процесса;
- `GET /api/events` — нормализованные карточки;
- `GET /api/sources` — состояние источников и статистика последнего запуска;
- `GET /api/import-runs` — журнал запусков и причины отклонений;
- `POST /api/imports/{source}` — ручной запуск выбранного адаптера.

React-интерфейс показывает:

- общий каталог мероприятий;
- поиск по названию, описанию и тегам;
- фильтр по формату;
- дату начала, завершения и регистрации;
- раскрываемую панель источников в порядке подключения;
- отметку успешно импортированного источника;
- количество полученных, валидных и отклонённых карточек;
- ручной запуск импорта;
- предупреждение о данных старше 48 часов;
- ошибку последнего запуска без удаления уже сохранённых карточек.

## 6. Реакция на краевые случаи и отказы

### 6.1. Изменился API или формат JSON

Если endpoint вернул другую структуру, пропали обязательные поля, стала некорректной пагинация или список неожиданно оказался пустым, декодирование либо контрактная проверка завершают цикл ошибкой.

Последствия:

1. источник получает статус `failed`;
2. время и описание ошибки записываются в журнал;
3. `last_success_at` остаётся прежним;
4. карточки последнего успешного импорта не удаляются;
5. интерфейс продолжает работать и показывает предупреждение только для проблемного источника.

Так изменение API не превращается в массовое удаление каталога.

### 6.2. Изменилась HTML/DOM-структура сайта

HTML-адаптеры проверяют не только селекторы, но и смысловой контракт: наличие секции, обязательных полей, ожидаемого payload и хотя бы одной валидной карточки.

- Если изменилась одна карточка, она попадает в `rejected`, остальные сохраняются, статус становится `partial`.
- Если исчезла ключевая секция, `data-testid`, Next.js payload или все карточки стали неразбираемыми, весь запуск становится `failed`.
- Для Codenrock и Kaggle отдельно контролируется успешный запуск Chrome и общий тайм-аут рендера.

В ходе RAT‑PoC разбор проверялся на сохранённых HTML/JSON-образцах и живых сайтах. По требованию к минимальной runtime-версии файлы `*_test.go` и `testdata` удалены из итогового репозитория. Поэтому после дальнейшего изменения адаптера обязательна повторная живая smoke-проверка источника.

### 6.3. Сайт недоступен

Сетевая ошибка, DNS-сбой, тайм-аут, `429` или `5xx` считаются временными отказами. HTTP-адаптеры делают ограниченное число повторов с задержкой; часть адаптеров учитывает `Retry-After`. Если источник не восстановился, запуск завершается как `failed`, а предыдущие карточки остаются доступны.

Ошибка одного источника не останавливает всю систему и не удаляет данные остальных источников. При автоматическом старте приложение переходит к следующему адаптеру.

### 6.4. Источник вернул `403` или потребовал авторизацию

Адаптер не пытается обходить авторизацию и не переключается на запрещённый внутренний API. Запуск считается неуспешным. Последний успешный снимок сохраняется, а в дальнейшем требуется пересмотреть допустимый публичный способ получения данных либо договориться с владельцем площадки об API.

### 6.5. Ограничение частоты запросов

Запросы выполняются с межзапросной паузой, ограниченным параллелизмом и защитными лимитами числа страниц. Ответ `429` повторяется только ограниченное число раз. Это предотвращает бесконечный цикл и снижает нагрузку на внешние сайты.

### 6.6. Некорректная карточка

Карточка отклоняется, если отсутствует устойчивый ID, название, подтверждаемая дата, обязательная ссылка или если даты противоречат друг другу. Причина сохраняется в запуске. Другие карточки того же источника продолжают импортироваться.

Если отклонены все карточки, запуск считается `failed`, а не `partial`, чтобы пустой новый результат не заменил рабочий снимок.

### 6.7. Дубли

Внутри источника записи дедуплицируются по UUID, slug или числовому ID. Повторный импорт обновляет существующую запись благодаря ключу `<source_id>:<source_event_id>`.

Автоматическое объединение одинакового мероприятия между разными источниками пока отсутствует. Одна и та же конференция на Devpost и HackList будет показана двумя карточками. Это осознанное ограничение PoC: межисточниковое объединение требует отдельной модели уверенности, чтобы не склеить разные мероприятия с похожими названиями.

### 6.8. Каталог изменился во время пагинации

Стабильные ID удаляют повторы между страницами. HackathonRadar дополнительно использует сортировку по названию, потому что сортировка по популярности меняется прямо во время обхода. Несовпадение заявленного и полученного количества формирует предупреждение в адаптере.

Текущее ограничение: поле `warnings` ещё не сохраняется в `ImportRun`; постоянно хранятся статус, счётчики, общая ошибка и причины `rejected`. Перенос предупреждений в журнал запусков — отдельная задача следующего этапа.

### 6.9. Одновременные импорты

Глобальная блокировка разрешает только один цикл. Второй ручной запуск немедленно получает `409 import is already running`. Это защищает файловое хранилище и ресурсоёмкие Chrome-адаптеры.

### 6.10. Сбой во время сохранения

JSON сначала полностью сериализуется во временный файл. Только после успешной записи временный файл переименовывается в основной. Ошибка записи не должна оставлять наполовину записанный `state.json`.

Если уже существующий `state.json` вручную повреждён, приложение сейчас завершает запуск с ошибкой декодирования. Автоматическое резервное копирование и восстановление повреждённого локального файла в PoC не реализованы.

### 6.11. Устаревшие данные

Интерфейс помечает источник, если последний успешный импорт был более 48 часов назад. Пользователь видит, что карточки доступны, но требуют повторной проверки. Это лучше, чем скрыто показывать старый снимок как свежий.

## 7. Проверки и доказательства

Во время RAT‑PoC каждый адаптер проверялся на контролируемых образцах ответа и двумя живыми запусками там, где требовалась проверка идемпотентности. Итоговый очищенный репозиторий содержит только runtime-код, поэтому перед публикацией изменений выполняются проверка компиляции и сборка интерфейса:

```bash
go build ./...
cd web && npm install && npm run build
```

Эти команды подтверждают собираемость, но не проверяют корректность парсинга изменившегося внешнего сайта. Для этого нужен отдельный живой импорт. Возврат автоматических контрактных тестов в CI рекомендуется перед командной или промышленной разработкой.

По контрольному локальному снимку от 16 октября 2026 года система содержала 378 карточек:

| Источник | Получено | Валидно | Отклонено | Статус |
|---|---:|---:|---:|---|
| Хакатоны.рус | 26 | 25 | 1 | partial |
| Codenrock | 29 | 29 | 0 | success |
| Hackathons.pro | 18 | 13 | 5 | partial |
| HackathonRadar | 221 | 220 | 1 | partial |
| Kaggle | 11 | 11 | 0 | success |
| HackList | 12 | 9 | 3 | partial |
| Devpost | 58 | 58 | 0 | success |
| Devfolio | 13 | 13 | 0 | success |

`partial` в этой таблице не означает отказ системы: валидные карточки сохранены, а неподтверждаемые записи изолированы с причинами отклонения.

## 8. Что уже доказано в рамках RAT‑PoC

- Один интерфейс адаптера подходит для восьми технически разных источников.
- Большинство каталогов можно читать без браузера и без учётных данных.
- Для JavaScript-каталогов пригоден контролируемый headless Chrome.
- Ошибка одного источника не разрушает общий каталог.
- Сломанный или пустой ответ не затирает последнюю успешную выборку.
- Невалидные карточки можно изолировать, не теряя валидные.
- Повторный импорт не создаёт дублей внутри источника.
- Пользователь видит свежесть и состояние каждого адаптера отдельно.
- Реальная выборка из восьми источников проходит через полный путь от внешнего сайта до карточки React-интерфейса.

## 9. Остаточные риски и следующий этап

| Приоритет | Риск или ограничение | Рекомендуемое действие |
|---|---|---|
| Высокий | Исчезнувшие из успешной выборки карточки не деактивируются | Реализовать source-scoped snapshot и soft delete только после полного успеха |
| Высокий | JSON-файл не рассчитан на несколько процессов и большой объём | Перенести `events`, `sources` и `import_runs` в PostgreSQL с уникальным ключом источника |
| Высокий | Изменения живых сайтов обнаруживаются только при запуске | Добавить планировщик, smoke-проверки и оповещения по `failed`, нулевой выборке и резкому падению количества |
| Средний | Предупреждения адаптеров не сохраняются | Добавить `warnings` в `ImportRun` и API журнала |
| Средний | В очищенном runtime-репозитории нет автоматических тестов адаптеров | Перед командной разработкой вернуть фикстурные тесты в CI или отдельный QA-пакет |
| Средний | Нет межисточникового объединения | Ввести отдельный слой matching по URL, названию, датам и организатору с оценкой уверенности |
| Средний | Chrome-адаптеры тяжелее и зависят от окружения | Зафиксировать версию Chromium в контейнере и вынести браузерные импорты в отдельный worker |
| Средний | Нет резервной копии локального состояния | До миграции в БД хранить предыдущий JSON-снимок и проверять целостность при старте |
| Организационный | Публичная доступность не равна разрешению на промышленный сбор | Согласовать условия использования, частоту запросов и при возможности официальные API |

## 10. Итог

RAT‑PoC подтвердил техническую реализуемость сервиса. Главный риск — неоднородность и нестабильность внешних источников — не устраняется полностью, но локализуется отдельными адаптерами, контрактной валидацией и стратегией last known good.

Текущий прототип уже подходит для демонстрации полного сценария и дальнейшей проверки продуктовых гипотез. Для перехода к эксплуатации важнее всего добавить деактивацию исчезнувших карточек только после полностью успешного цикла, перенести состояние в PostgreSQL и автоматизировать мониторинг изменений контрактов источников.

## 11. Дополнение: лаборатория отказов

В текущем репозитории добавлена локальная страница `/parser-lab` и `POST /api/lab/run`. Страница позволяет выбирать один из восьми источников и воспроизводить 503, 403, 429, тайм-аут, смену формата, смену обязательного поля/DOM, повреждённую карточку, пустой ответ и восстановление. Каждый запуск использует отдельный снимок в памяти; рабочий `data/state.json` и внешние сайты не изменяются. На экране видны ответ заглушки, результат импорта, состояние до и после, дата последнего успешного цикла и проверки сохранения карточек.

Для шести HTTP-адаптеров заглушка отвечает по локальному HTTP при отказе доступа, тайм-ауте, изменении формата/поля и пустом списке. У Devfolio и HackList дополнительно проходят через настоящий парсер сценарии повреждённой карточки и восстановления. Для остальных четырёх HTTP-адаптеров эти два сценария, а для браузерных Codenrock и Kaggle все сценарии, подаются на границе адаптера и проверяют общий код оркестрации и хранения. Их конкретные парсеры нужно проверять отдельными фикстурными тестами. `go test ./...` и `npm run build` являются проверками этой добавленной лаборатории; живой импорт остаётся отдельным доказательством актуальности внешних сайтов.
